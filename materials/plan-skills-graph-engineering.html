Graph Engineering — from idea to commit

A swarm of role agents drives one change from a sentence to a commit. This is the file that declares its shape, the tool that enforces the declaration, and an honest account of where the enforcement stops.

The practice

Graph engineering is a loop, not a diagram

The name suggests a picture. It is not a picture — it is four steps that run on every change, and the fourth is the one that makes the other three worth doing. Skip it and the declaration quietly decays back into documentation.

01 · DECLARE One file, or none Every node, every edge, every routing condition in one machine-readable artifact. Anything else that describes the shape is a copy.
02 · GENERATE Never transcribe Diagrams and docs are emitted from the declaration, between markers. A hand-drawn diagram is a second source of truth waiting to drift.
03 · VALIDATE Resolve against disk Does every declared node exist? Does every edge land somewhere? A violation is a non-zero exit, not a review comment.
04 · DRIFT-CHECK Close the loop CI regenerates and fails if the output differs. This is the step that converts a convention into a constraint.

The assertions

Stripped of the vocabulary, it asserts three things

Three principles, referred to throughout this document as Topology (P1), Context (P2) and State (P3). Every claim below is tagged with the one it serves — and one important property of this system serves none of them, which is stated rather than hidden.

TOPOLOGY (P1) The topology is an explicit artifact Which nodes exist, what routes between them, under what condition — readable as one thing, and generated rather than transcribed.
CONTEXT (P2) Each node gets its own clean context Its own prompt, its own tools, its own evidence — so one agent's working memory does not pollute another's. The unit of isolation is the node, not the conversation.
STATE (P3) State crosses boundaries only through declared edges A schema, not a directory convention. What a node may read and write is written down and checkable — not a sentence in a prompt asking it to behave.
what a topology cannot express

A topology can show you that three branches run in parallel. It cannot show you whether those branches are independent — and that is the property that decides whether a voting gate means anything. Hold on to this; it returns at the end.

Applied · what the swarm is

One change, six phases, two places a human has to say yes

The subject of the rest of this document is a swarm of role agents that takes a request — a feature, a fix, a refactor — and drives it to a commit. Files under plans/, never chat messages, are the single source of truth; agents are handed file paths, not summaries.

Topology (P1) · step 01 of the loop

What is inside graph.json, and what each part binds to

The file is not documentation that happens to be machine-readable. Every field below resolves to something on disk, and validate fails when the resolution fails.

Who writes it, and what it actually is

WHO · a human, by hand It is not generated from anything. Someone edits it when the swarm's shape changes, then runs sync. Its own header says so: “edit this file, then regenerate — never hand-edit a rendered diagram.”
WHY · to break a three-way tie The topology can otherwise live in two READMEs and in the orchestrator's control flow. All three describe the same lifecycle; none is authoritative, so nothing can detect that they have drifted apart.
WHAT · a manifest, not a runtime Nothing executes it. graph.json is the AST, starter is the eval loop — it is not a node, it is what walks the graph — and graph.py is the type checker. An edge is enforced at review time by CI, not at runtime by construction. 
$ python3 plugins/plan/lib/graph/graph.py render svg   # figure 3, regenerated
$ python3 plugins/plan/lib/graph/graph.py validate     # every binding above

State (P3) · mechanism

A skill is a node with declared edges

A skill's authority can live in prose — “read-only on source”, “never commits”. Those sentences are still in the skill files, but the same facts are declared in graph.json where a script can read them. architect is the clearest case: it reads two things, writes three, and is explicitly denied one.

The other half of State (P3) is the run itself. state.json, whose schema lives in lib/graph/STATE.md, records the phase, both gate decisions, per-node status with report paths, and per-group tasks, audit rounds and commit SHAs. It is written only by starter and read by everyone resuming — which is what lets the phase be read rather than re-derived by inspecting a directory.

Context (P2) · mechanism

Clean context, extended inside the fan-out

Per-node isolation is this swarm's strongest property. The part that is easy to miss is isolation within a node's fan-out. A panel that dispatches one prompt three times has three branches sharing one prompt, one model and one reading assignment — a fan-out that is wide but not independent. Each panel here hands its three skeptics disjoint evidence instead.

the pre-flight check that keeps it honest

Every panel run must first pass the asymmetry test: name one finding only that lens could reach. If you cannot, merge it and run two — a panel of near-clones is worse than an honest pair, because it manufactures corroboration. The test is lifted in spirit from plan-deliberator's Core Principle 1.

At a glance

Exactly one file defines, exactly one enforces, and everything else obeys or derives. That single-writer property is the whole point: the alternative is three files that each claim to be the topology.

File by file

What each file declares, and what fails when it stops being true

plugins/plan/graph.jsondeclaration P1 · TOPOLOGYP3 · STATE

What it holds

16 nodes with kind, phase, skill, agent and alternatives; 25 edges with conditions and labels; 2 gates; 5 invariants; per-node reads, writes and must_not_write; and each panel's lens roster with its asymmetry statement. 503 lines of JSON and nothing else — no code, no imports, no runtime.

Invariants declared

  • · only starter commits
  • · only engineer + simplifier write source
  • · identical prompts are a defect, not a config
  • · human gates cannot run inside a workflow
  • · dispatch file paths, never summaries
Why not in the skill frontmatter: the obvious alternative is a reads:/writes: block in each SKILL.md. Putting them in both places would create a second hand-maintained copy of the same facts — which is exactly the defect Topology (P1) exists to prevent.
lib/graph/graph.pytooling · the enforcer P1P2P3

What it does

Stdlib only, so it runs wherever the plugin is installed and on either harness. validate checks the declaration against disk; render ascii|mermaid|svg draws the graph; sync rewrites the generated blocks in both READMEs; sync --check exits non-zero when one is stale. That last flag is step 04 of the loop.

Failures it produces

  • ✗ declared skill or agent missing from disk
  • ✗ edge pointing at an unknown node
  • ✗ node with no inbound edge
  • ✗ node claiming write authority it lacks
  • ✗ lens declared but absent from its prompt
  • ✗ prompt file reverted to identical dispatch
Both lens checks were negative-tested. Renaming a lens in graph.json, and appending “dispatch this three times, unchanged” to a prompt file, each produce a named error and exit 1.
lib/graph/STATE.mdschema P3 · STATE

What it defines

state.json per milestone: run_id, phase, gate decisions, per-node status with report paths, and per-group tasks, audit rounds and commit SHAs. Written only by starter; read by everyone resuming.

Two fields worth knowing

cross_lens — how many confirmed findings were reached by more than one lens. The number that says whether a panel produced independent corroboration or one opinion twice.

reason — required whenever a node's status is skipped. Absence of a report is otherwise ambiguous between not-run, crashed and deliberately skipped.

skills/starterorchestrator · the eval loop P1P3

What it declares

The state machine dispatches every node the declaration names — including the validators and deliberators. Two clauses carry the weight: the topology is declared, not remembered (follow graph.json) and the phase is read, not inferred (read state.json). The engineer ⇄ auditor cycle carries a 3-round cap.

Its boundary

“Never skip a gate silently. If you deliberately skip a validator or a deliberator, say so and record it in state.json. An unrecorded skipped gate is indistinguishable from a gate that passed.”

Held exclusively

  • ✓ only node that runs git commit
  • ✓ holds both human gates
  • ✓ dispatches file paths, not summaries
Why this file carries the most risk: by the Berkeley multi-agent failure taxonomy, a documented-but-undispatched gate is a system design failure — the 44.2% category, against 2.7% for anything aggregation-related. A gate that exists in the docs and not in the dispatcher is the highest-leverage defect this architecture can have.
agents/supervisoragent P1P3

What it declares

The initialPrompt bootstrap does not inspect the milestone directory to guess a phase. It reads state.json, reconciles it against graph.json, and reports any gate recorded as skipped or outstanding before recommending an action.

Its standing note

“The topology is a file, not a memory.” Skipping a declared node is a decision to state out loud and record — not one to make silently. The README diagrams are generated; never hand-edit them.

Single-sourced: the body delegates to ${CLAUDE_PLUGIN_ROOT}/skills/starter/SKILL.md, so the state machine is shared between the skill and agent families rather than restated in both.

Enforcement · step 03 and 04 of the loop

Every invariant sits on one of three rungs

Declaring a rule is not enforcing it. Five invariants are written into graph.json; three of them produce an exit code; two are prose and are labelled as prose. The distance between rung 1 and rung 2 is the entire value of the tooling.

5 declaredWritten into graph.json as a named invariant.
3 checkedgraph.py exits 1 the moment it is broken.
2 trustedDeclared and labelled as prose — no check exists.
✔
Only starter runs git commit — it is the only node holding a user-facing turn in which approval can be obtained. violating it → node 'x' declares it commits but is not held by starter · exit 1
✔
Only engineer and simplifier write repository source. violating it → node 'x' declares it writes repository source · exit 1
✔
Every panel node declares n distinct lenses — identical prompts are a defect, not a configuration. violating it → lens declared but absent from <prompt_file> · exit 1
○
Human gates cannot run inside a scripted workflow — a workflow run takes no mid-run user input. unenforceable — no file records how the swarm was invoked
○
Agents are dispatched with file paths, never with a prose summary of an artifact. unenforceable — the violation is a message, and messages are not on disk

Structural checks ride along on rung 2 alongside the three named invariants: unknown node · unreachable node · missing SKILL.md · a gate that is not of kind human-gate · a stale generated block.

$ python3 plugins/plan/lib/graph/graph.py validate
graph.json OK — 16 nodes, 25 edges, 3 lens-partitioned panels, 2 human gates

$ python3 plugins/plan/lib/graph/graph.py sync --check
all generated blocks are up to date

One test decides the rung: does breaking it leave a mark in a file? The last two can only be broken in transit — in a dispatch message that nobody writes down.

Honest accounting

Three ways past the ladder entirely

Everything above describes what the declaration catches. This section is what it does not, stated plainly, because a conformance claim that only lists its successes is not a conformance claim.

01 · NOT DECLARED The check runs one way validate walks the declaration and asks “is this on disk?” Nothing walks disk and asks “is this declared?” 20 skills exist under plugins/plan/skills/; 13 are named in graph.json — the 11 node skills plus two alternatives. Add a skill, forget to declare it, and the build stays green.
02 · NOT EXPRESSIBLE Independence has no syntax Giving each panel's three skeptics disjoint evidence is not something any topology language can express. Correlated judge panels run 8–22 points below the independent-voting ideal, and no aggregation algorithm recovers more than 11% of that gap. That is a property of the information flowing through the edges, not of their shape.
03 · NOT MEASURED The payoff is an inference That partitioned lenses catch more than three identical ones is believed, not shown. Falsify it: re-run one shipped milestone both ways and diff the confirmed finding sets. If cross_lens comes back zero, the partition bought nothing.

Graph engineering names two real defects here — a drifted topology and undeclared state — and both are now on rung 2. It is silent on the third, which is the one most likely to change what the gates actually catch.
