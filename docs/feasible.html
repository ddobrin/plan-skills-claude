Can the Plan Swarm go AI‑native?

Feasibility assessment of adopting Anthropic's AI‑Native SDLC Playbook in the plan plugin swarm.

Repo: plan-skills-claude @ a54fa10 (branch explore) Playbook: Louis Claxton, 21 Aug 2026 Assessed: 24 Sep 2026 Scope: Plan → Deploy in full · Maintain as roadmap Packaging: plugin + opt‑in project templates

Feasible, and a good fit. The swarm is already AI‑native in the middle of the lifecycle and pre‑AI at both ends.

The playbook's backbone (each stage commits a Markdown artifact the next stage reads, and humans approve at gates) is the swarm's founding design. spec.md → plan.md → code with a mandatory human gate already exists, and the adversarial validators beat the playbook's review model. What's missing is everything around the agents: deterministic enforcement (hooks), a committed evidence trail, a PR‑based delivery stage, evals for the swarm's own prompts, and an entry point that isn't a human typing a request.

None of the gaps needs a redesign. Every required change either adds a new artifact or hook, or tightens an existing prompt. The two human gates, the file‑based handoffs, and the validator/deliberator machinery all stay.

The single most important change: move the swarm's rules from prose to mechanism. Today "only the auditor commits" and "stop for approval" exist only as sentences in prompts. The engineer holds Bash and could run git commit; nothing stops it. The playbook's governance model rests on deterministic hooks and committed evidence. Fix that first; everything else builds on it.

2 · What the playbook asks

Its premise: AI made writing code cheap, so the bottleneck moved to the human‑speed stages around it. The playbook rebuilds the SDLC as a loop of six stages. Each stage commits an artifact the next one reads, and the chain of commits is the audit trail.

1 · Plan
intent.md
Originator brainstorms with Claude; PO reviews & commits.
2 · Design
spec.md
Requirements + design in one session, constrained by policy skills.
3 · Build
plan.md · code · CLAUDE.md
Plan mode first; skills, hooks, worktrees, subagents.
4 · Test
tests · evals
Self‑verification loops; continuous evals of agent config in CI.
5 · Deploy
PR + findings
AI PR review vs REVIEW.md; hook approval gates; headless CI.
6 · Maintain
intent.md (auto)
Detection bands breach → Claude diagnoses → writes intent.md.

Top border = current swarm fit: strong partial gap

Governance rests on four shifts: separation of duties (the agent that writes can't approve), policies as code (skills), deterministic enforcement (hooks and approval gates), and managed settings. Evidence comes from OpenTelemetry transcripts, PR history, git history, and CI logs.

5 · Where the swarm is already ahead: keep these

Quorum review with severity calibration

The playbook's PR review is "Claude reviews, ranked by severity". The swarm uses 3 independent skeptics, a 2‑of‑3 gate via lib/tally.py, surfaces the unconfirmed tail, and reports corrected severity. That's a stronger review engine than the playbook describes. Make it the PR reviewer.

Validation at every artifact, not just the PR

Spec and plan validators catch defects before code exists. The playbook reviews at PR time only. plan-validator's first_domino is exactly the "cheap early catch" the playbook's speed goal needs.

Deliberation for siloed knowledge

The playbook's PO "resolves flagged concerns with policy owners" by hand. spec-deliberator formalizes that with disjoint stakeholder bundles and a recorded outcome. It's the natural home for policy‑owner input.

Anti‑shortcut auditing

Hunts for TODOs, gutted or skipped tests, and hardcoded outputs. The playbook's "feedback loops" don't address reward‑hacking at all. This is a differentiator.

Files over chat

The supervisor passes file paths, never summaries. Every artifact the playbook wants committed already exists as a file. What's missing is committing them at the right moments.

Tool allowlists as capability contracts

The playbook's "subagents with scoped context and tool limits" already exists: the architect and PO can't run Bash. Extend the pattern, don't replace it.

9 · Phased roadmap

Phase 1: Make the rules real do first

P‑1 · P‑2 · P‑4 · P‑10 (tally fixtures + gate‑discipline scenarios only) · est. 1–1.5 weeks

Hooks, committed evidence, reviewers stop fixing, and the first evals. No new stages yet. After this, every existing gate is enforced and leaves a record. Build the minimal evals first, because this phase rewrites the prompts they protect.

Exit: a deliberate git commit from an engineer is blocked; approvals.md and audit.md appear in history; evals run green on both forms.

Phase 2: Front door and back door

P‑5 · P‑7 · P‑8 · T‑1 · T‑2 · T‑4 · est. 2 weeks

Add intent.md at the start and a PR at the end. The swarm now spans the playbook's Plan → Deploy, with implementation-validator as the policy‑aware PR reviewer and tiered gates.

Exit: one real milestone runs intent → merged PR with every artifact committed, and REVIEW.md findings posted on the PR.

Phase 3: Scale and learn

P‑3 · P‑6 · P‑9 · P‑11 · P‑10 (full) · T‑3 · T‑5 · est. 1.5–2 weeks

Policy skills, worktree parallelism, the CLAUDE.md feedback loop, metrics, and the full eval suite in CI.

Exit: a baseline of lead‑time and rework metrics from lib/metrics.py; prompt PRs gated on eval pass rate.

Phase 4: Close the loop roadmap

T‑6 · headless triage entry · incident → eval · depends on Phases 1–3

A detection breach invokes a triage agent that can only write plans/intents/*.md with evidence. The PO triages as a human. Accepted intents flow through the normal gates. Merged fixes add an eval case. Prerequisites: production signals the plugin can't own, and a team willing to operate bands.yaml.

Feasibility: moderate. The mechanics are simple, because the swarm's intake is just a file. The operating model is the hard part.

Estimates assume one engineer familiar with the repo, and include keeping agents/skills/READMEs in sync. They aren't commitments.

12 · Open decisions for the owner

  1. Where does an approval token live? A file in the milestone (auditable, but forgeable by an agent with Write) or an environment/hook‑side secret (stronger, but less visible). Recommendation: the approvals.md entry for the record, plus a hook‑checked nonce the supervisor can only obtain from a user prompt.
  2. Locked‑down orgs. If admins enforce allowManagedHooksOnly, P‑1 does nothing unless the platform team adopts lib/gate.py as a managed hook. Do you ship the gate as a documented managed hook from day one?
  3. PR host. Is GitHub the only target? P‑7 and T‑2 assume gh. GitLab needs a parallel template.
  4. One source per role? Resolving G12 (generate skills from agents, or the reverse) before Phase 1 roughly halves the edit cost of everything after it.
  5. Direct‑commit mode. Keep a "local, no PR" mode for solo use, or make the PR stage mandatory?
