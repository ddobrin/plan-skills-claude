The AI‑Native SDLC with plan‑swarm@3.0

How the plan plugin for Claude Code implements an AI‑native software development lifecycle: agents do the work, people make the decisions, hooks hold the authority, and git keeps the record.

Plugin plan 3.0.0 Topology plugins/plan/topology.md (plan‑swarm@3.0) Reference: The AI‑Native SDLC Playbook 25 Sep 2026
plan‑swarm@3.0 takes a change from intent to merged pull request through a fixed sequence of stages. Each stage commits one Markdown artifact that the next stage reads. Specialist agents write the intent, spec, plan, code, and audit. The developer makes six decisions, each by typing an exact approval phrase. A control plane of Claude Code hooks turns each phrase into a single‑use approval and refuses every commit, push, or tag that lacks one. Every approval lands in a ledger that is committed with the change it authorizes, so the milestone's state and its audit trail are both just git log.

What "AI‑native" means here

The playbook's premise is that agents made writing code cheap, so the bottleneck moved to the human‑speed work around it: deciding what to build, reviewing it, and trusting it. plan‑swarm answers each part of that:

Artifacts, not meetingsEvery stage ends in a committed file: intent.md → spec.md → plan.md → code + audit.md → PR. The next agent reads the file, not a chat summary, so any session can stop and any other can resume.
People decide, agents executeAgents ask the questions, write, build, verify, and review. People approve intent, spec, plan, each commit, the PR, and the release. Nothing crosses those lines without them.
Mechanism, not promisesThe rules that matter are enforced by hooks and a git hook, not by prompts asking agents to behave. Prompts carry judgment; code carries authority.

The control plane

One Claude Code hook per event plus three git hooks, all standard‑library Python. They are active in repositories that contain plans/swarm.md, and stay active (failing closed) if that file disappears after swarm-init marked the repository.

HookScriptResponsibility
SessionStarthealth.pyHeartbeat; refreshes the git hook's copy of the gate; tells the session whether enforcement is active.
UserPromptSubmitapprove.pyIf the whole prompt is an approval phrase, mints a single‑use approval bound to HEAD (15 min) and appends a row to approvals.md.
PreToolUsegate.pyConsumes approvals for commits, first PR pushes, and tags; blocks default‑branch and force pushes, history rewrites on swarm branches, hook bypasses, writes to protected files, and engineers before plan approval. Follows cd inside a command.
git pre-commit · pre-merge-commitgate.py --git-hookSecond layer for commits, whatever started them: allowed only with the one‑time, 60‑second ticket the first layer issued, and a plans‑only approval cannot carry code. WIP is exempt only inside the swarm's own linked worktrees.
git pre-pushgate.py --pre-pushSecond layer for pushes: only fast‑forwards of swarm/{m} in which every new commit's parent matches an intent/spec/plan/commit row of the ledger (a pr row authorizes only the ledger‑only commit that records it; the first push also needs that row). Other branches and tags are refused while a swarm session is active, so people can still push their own work when Claude Code is not running.

Fail closed: if plans/swarm.md is invalid, or missing after activation, gated operations are refused and every other check still runs; any internal error in the gate refuses the tool call (exit 2). If an organization disables plugin hooks, the heartbeat goes stale, health.py --status reports enforcement off, and the supervisor refuses gated steps.

Threat model

The local control plane is a guard against well‑meaning agents that try to unblock themselves: the realistic failure of an AI‑native workflow. It is not a sandbox against a determined adversary: an agent with shell access runs with the same operating‑system privileges as the hooks and could, with deliberate effort, write files the parser does not recognize. The authoritative controls are therefore server‑side: branch protection on the default branch, the CI ledger check, and code‑owner review of every PR. The local layers make the approved path the only easy path, and make every deviation visible.

The evidence chain

The playbook's governance model says "the chain of commits is the audit trail: who asked for what, what the agent produced, and who approved it." In plan‑swarm that chain is literal: each approval is bound to the HEAD it was typed at, which is exactly the parent of the commit it authorizes.

The approval hook stages the new ledger row the moment the phrase is typed, so the row always ships inside the commit it authorizes. Only intent, spec, plan, and commit rows authorize commits; a pr row authorizes the first push plus the single ledger‑only commit that records it, and a release row authorizes the tag (its row is committed with the next milestone's intent commit).

Beyond the ledger, each milestone folder holds the reasons: the intent and its research, the spec and every validation or deliberation report (re‑runs preserved as -r2), the plan with its tier, every audit round, and usage.md with the cost of each dispatch and every offered check the developer declined, with the tier it was declined at.

Parallel build

  • The architect groups tasks so that tasks in one group touch disjoint files.
  • For each task the supervisor runs worktree.py create: branch swarm-wip/{m}/{task}, checkout under .swarm/worktrees/ (excluded locally), starting at the milestone's HEAD. Up to engineers.max_concurrent (5) engineers run at once.
  • Engineers work only in their worktree, may make WIP commits there, and report their steps (they do not edit plan.md, so parallel tasks never conflict on it).
  • worktree.py squash auto‑commits leftover WIP, refuses to integrate if two tasks touched the same file or a task touched plans/ (a plan defect: Path B), and otherwise stages the whole group with git merge --squash, no commit. The auditor audits exactly the diff the developer will approve.

The quality system

Test‑first by constructionEvery plan task starts with a test step; engineers work Red → Green → Refactor; the auditor fails any new behavior without tests, and hunts TODOs, skipped or gutted tests, and hard‑coded answers.
Independent skepticsSpec, plan, and implementation validators each dispatch 3 skeptics with no shared context; tally.py keeps findings 2 of 3 agree on and reports the rest. The implementation validator's key output is calibrated severity.
Deliberation for siloed knowledgeDeliberators give delegates deliberately different knowledge (stakeholder bundles, code territories) and drive them to one revised artifact, deciding trade‑offs a vote cannot.

The tier is proposed at intent, re‑checked at plan and on the real diff before the PR, and can only rise automatically. The developer confirms it in approve plan; lowering it requires writing tier=…, so the choice is on the record. Tiers recommend; they never force a check.

Continuous evals

The playbook asks teams to regression‑test the agent's own configuration whenever it changes. plan‑swarm does this in five layers for its own prompts and control plane. The plugin's CI runs L0 on every pull request and push to main that touches plugins/plan/; L1–L4 are real Claude sessions and run on pull requests only. Case format and commands: plugins/plan/evals/README.md.

These evals test the plugin, not your repository. The CI that swarm-init installs in a target repository (templates/ci/plan-swarm.yml) runs the ledger check, the REVIEW.md review, and the tier-gated validator panel; it does not run evals.

Adopting it

  1. /plugin marketplace add ddobrin/plan-skills-claude and /plugin install plan@plan-skills. Until 3.0 is published there, load it from a checkout with claude --plugin-dir <checkout>/plugins/plan and disable the installed 2.1 copy.
  2. In the repository, type /plan:swarm-init: plans/swarm.md, the three git hooks, and optionally REVIEW.md, .github/workflows/plan-swarm.yml, and an AGENTS.md skeleton (skipped when a CLAUDE.md exists). Nothing is overwritten.
  3. Fill in the build and test commands in AGENTS.md (or your CLAUDE.md; with both, CLAUDE.md must import @AGENTS.md), tune the tier rules and policy skills in plans/swarm.md, and commit.
  4. For PR review in CI, connect GitHub to Vertex AI with Workload Identity Federation (secrets GCP_WORKLOAD_IDENTITY_PROVIDER and GCP_SERVICE_ACCOUNT; the service account needs roles/aiplatform.user), and protect the default branch (require the ledger and review checks and a code‑owner review).
  5. Where plugin hooks are disabled by policy, follow templates/managed-settings.example.md.
  6. Start Claude Code as the supervisor, claude --agent plan:supervisor (or say "be the supervisor"). Every role then runs as a subagent with its own context; approval phrases count only when you type them in this main session. For solo or offline work set delivery.mode to local.

Limits and roadmap

  • Local enforcement is a guard, not a sandbox. The PreToolUse gate reads shell command text and refuses what it cannot recognize; the git hooks re‑check commits and pushes by any route. A determined agent could still, with deliberate effort, write the store or ledger with a script the parser does not flag. Branch protection, the CI ledger check, and code‑owner review are the authority.
  • No caller identity. Hook input does not say which subagent made a call, so file protections are path‑based, not role‑based.
  • Managed‑only hook policies disable plugin hooks; the swarm then refuses gated steps until the gate is adopted as a managed hook.
  • Maintain loop (future): the triage agent, bands.md detector, and intent‑PR workflow are specified in topology.md and architecture.html §14 but not built.
