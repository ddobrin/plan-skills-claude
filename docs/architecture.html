plan‑swarm@3.0: end‑state architecture

The whole process as it should run once the swarm adopts the AI‑Native SDLC: every stage, gate, artifact, and control, and how they fit together.

Status: proposed target, not implemented Baseline: a54fa10 · companion to feasible.html Playbook: The AI‑Native SDLC Playbook Date: 24 Sep 2026
As built (plugin 3.0.0). This design is implemented; ai-dlc.html describes the system as it now runs. Refinements made while building it:
  • Worktree branches are swarm-wip/{m}/{task}, not swarm/{m}/w/{task}: git cannot create a ref below an existing branch.
  • In pr mode swarm/{m} is created when the intent is accepted (not at plan approval), so the intent, spec, and plan commits ship inside the PR.
  • Approvals, tickets, and the heartbeat live in .git/plan-swarm/ (not ${CLAUDE_PLUGIN_DATA}) so the git pre-commit hook, which runs outside Claude Code, can read them; the git hook trusts a short‑lived ticket from the first layer instead of an environment marker.
  • Worktrees are created by lib/worktree.py under .swarm/worktrees/ from the milestone HEAD (the Agent tool's worktree base is not configurable); engineers in worktrees report steps and the supervisor ticks plan.md, so parallel tasks never conflict on it.
  • The cost log is written through lib/usage.py by the supervisor (the SubagentStop payload carries no usage totals); the managed‑settings template is templates/managed-settings.example.md.
  • The gate is active only where plans/swarm.md exists (and fails closed if it disappears after activation), follows cd inside a command, and classifies pathspec commits by their paths.
  • An independent security review found bypasses in the first gate; the hardened gate refuses unrecognized git forms, adds pre-merge-commit and pre-push hooks that check every pushed commit against the ledger, and the approval hook stages the ledger row into the commit it authorizes. The threat model is explicit: local layers guard against well‑meaning agents; branch protection, CI, and code‑owner review are the authority.
In one paragraph. A human or, later, a detector drops an intent.md into an inbox. The supervisor walks it through the unchanged spine: intent → spec → plan → 🛑 approve → build → audit → 🛑 commit → PR → release. Each step commits its artifact. Judgment stays in prompts (roles, validators, deliberators, all still offered). Authority moves into a control plane of hooks: a real human prompt mints a single‑use approval nonce, and a gate consumes it before any commit, push, or tag. Engineers build in parallel worktrees. Work lands as a PR reviewed against REVIEW.md. Every approval is written to a ledger by the mechanism, not by an agent, so the milestone's state and its audit trail are both just git log.

1 · Design principles

Artifacts are the stateNo hidden state file. A milestone's phase is derived from which committed artifacts and ledger entries exist, so any session can resume.
Prose for judgment, mechanism for authorityPrompts decide what is good. Hooks decide what is allowed. No prompt sentence is the only thing standing between an agent and a commit.
Humans own intent, approval, mergeFive human decisions per milestone: accept intent, accept spec, approve plan, approve each commit, merge the PR. Plus release.
Reviewers never writeValidators and the auditor report. Only the engineer changes code, and only the auditor makes deliverable commits.
Every step leaves a commitThe chain of commits is the audit trail: who asked (intent), what was agreed (spec, plan), who approved (ledger), what shipped (PR).
One source, many formsEach role is written once. Agent and skill forms are build outputs, and evals verify both.

4 · Milestone state machine

State is derived, never stored. The supervisor (and lib/metrics.py) computes it from committed artifacts and ledger entries. This is today's orientation step made precise, and it means a crashed or new session always resumes correctly.

Resume algorithm (supervisor orientation)

  1. Read plans/swarm.md, 00-ROADMAP.md, plans/intents/, and every active_milestones/*/.
  2. For each milestone, take the furthest state whose evidence exists and whose predecessors' evidence also exists. A gap (e.g. a plan.md without ledger: spec) is reported as an inconsistency, not skipped.
  3. Check the control‑plane heartbeat (§5.1). If it's missing, report "enforcement off" before anything else.
  4. Report (milestone, state, next action, agent, required human decision) and wait. This is unchanged from today.

5 · Control plane

A small set of deterministic scripts in lib/, wired by the plugin's hooks/hooks.json. It holds all authority. Everything it decides is logged, and nothing it enforces depends on a model following instructions.

5.2 Approval protocol

Grammar (case‑insensitive, the whole prompt must match):

approve intent  <slug> as <moniker>
approve spec    <moniker>
approve plan    <moniker> [tier=routine|elevated|critical]
approve commit  <moniker> g<n>
approve pr      <moniker>
approve release <version>

Requiring the whole prompt to match is deliberate. "yes", "ok", or an approval phrase buried in a paragraph never mints anything. The supervisor always prints the exact phrase to type.

Nonce record (in ${CLAUDE_PLUGIN_DATA}/approvals/<repo-id>/, outside the repo, guarded by gate.py --guard):

{ "id": "n_7f3c9a", "kind": "commit", "moniker": "auth-mvp", "group": 2,
  "head": "4e1b0c2", "tier": "elevated", "who": "dan@example.com",
  "created": "2026-09-24T14:02:11Z", "expires": "2026-09-24T14:17:11Z", "used": false }

Binding to HEAD means an approval can't be spent after unrelated commits land. The approved diff is shown, but it isn't cryptographically bound, because the auditor stages after approval. Binding the staged tree hash is a listed hardening option (§17).

7 · Build topology: worktrees and branches

  • Dispatch. The supervisor dispatches up to engineers.max_concurrent (default 5) engineers per message with isolation: "worktree", based on swarm/{m} HEAD. Larger groups run in batches.
  • Integration. After the batch, the supervisor runs git merge --squash --no-commit for each worktree branch into the milestone checkout. File overlap is impossible if the plan is right, so a conflict is treated as a plan defect → Path B.
  • Why squash: the audit sees exactly one group diff, the commit gate approves exactly that diff, and history holds one commit per approved group.
  • Cleanup. Worktree branches are deleted after the group commit. Their WIP never reaches the remote (the policy denies pushing swarm-wip/*).
  • Local mode. Same flow with the current branch standing in for swarm/{m}, and no PR.

Contract: bands.md

The playbook calls this file bands.yaml. It follows the same Markdown + fenced‑JSON convention as swarm.md, so the CI detector needs only built‑in Python. Service owners write why each band is set where it is.

# Detection bands

## ci-flaky-rate
Owned by platform. 7‑day window smooths weekend noise.

## p95-latency-checkout
Owned by checkout. Fixed baseline from the Q3 load test.

```json bands-config
  "signals": [
    { "id": "ci-flaky-rate", "source": "github-actions",

      "band": { "baseline": "rolling_mean", "sigma": "rolling_std" },
      "tiers": { "log": 1, "diagnose": 2, "propose": 3 }, "owner": "team-platform" },
    { "id": "p95-latency-checkout", "source": "prometheus",
      "query": "histogram_quantile(0.95, ...)",
      "band": { "baseline": "250ms", "sigma": "40ms" },
      "tiers": { "log": 1, "diagnose": 2, "propose": 3 }, "owner": "team-checkout" }
  ]

```

Guardrails

  • The triage agent can write only intents: tools Read/Grep/Glob/Write, and gate.py allows writes under plans/intents/ only. It has no Bash, so it can't commit. The workflow's deterministic step commits and opens the PR.
  • No autonomous remediation. The playbook allows quarantining flaky tests or opening reverts at 3σ. That is left as an explicit future extension that needs its own tier and approval kind.
  • Evidence required. source: triage intents must include the breached signal, its window, and the queries used. The PO closes intents that don't.
