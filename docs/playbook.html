The Plan Swarm Playbook

How to take a feature, fix, or refactor from idea to merged PR with the plan swarm, one stage at a time.

Describes plan‑swarm@3.0 (plugins/plan/topology.md) Design: architecture.html · Build order: implementation-plan.html
Status. This playbook describes plugin 3.0.0 (plan‑swarm@3.0), which implements everything below except stage 15 (Maintain), still future. The as‑built system is described in ai-dlc.html.

What the swarm is

The plan swarm is a team of Claude agents, each with one job: product owner, architect, engineers, auditor, and reviewers. A supervisor runs the team and walks your change through a fixed sequence of stages. Every stage writes a file under plans/, and the next stage reads that file. Nothing important lives only in the chat.

You decideSix times per change you type a short approval phrase: accept the intent, the spec, the plan, each commit, the PR, the release. Nothing moves past those points without you.
The swarm does the workIt asks the questions, writes the spec and plan, writes the code test‑first, audits it, and prepares every commit and the PR.
Git keeps the recordEvery stage's file is committed, and every approval is logged by a script, not by an agent. The history shows who asked, what was agreed, who approved, and what shipped.

Running example. Throughout this guide we'll add rate limiting to the login endpoint, milestone name login-rate-limit.

One‑time setup

  1. Install the plugin (once per machine): 
    /plugin marketplace add ddobrin/plan-skills-claude
/plugin install plan@plan-skills

    Until 3.0 is published to the marketplace, the installed plugin is the older 2.1 and has no swarm-init. Load the 3.0 plugin from your checkout for each session instead, and disable the installed plan@plan-skills in the /plugin menu so only one plan plugin is loaded:

    claude --plugin-dir ~/path/to/plan-skills-claude/plugins/plan
  2. Prepare the repository (once per repo). In Claude Code, type /plan:swarm-init (or say set up the plan swarm). It is a skill, not a subagent, because it is a short interactive setup. It previews what it would install, asks which pieces you want, never overwrites a file, and then adds:
    • plans/swarm.md: your settings (delivery mode, engineer limit, risk rules, policy skills). Read it. The explanations sit next to the values.
    • Three git hooks, pre-commit, pre-merge-commit, and pre-push: a second layer that re‑checks commits and pushes, whatever started them.
    • REVIEW.md, .github/workflows/plan-swarm.yml, and an AGENTS.md skeleton (skipped if you already have a CLAUDE.md), for PR review in CI. Optional but recommended.

    You can also run the installer yourself: python3 <plugin>/lib/swarm_init.py --dry-run, then --only swarm,hook,review,ci.

  3. Fill in AGENTS.md (or your existing CLAUDE.md) with your build and test commands. The auditor runs exactly what's written there. If you keep both files, start CLAUDE.md with the line @AGENTS.md; otherwise Claude Code never loads AGENTS.md.
  4. Commit the setup yourself, like any other change.
Each session, the supervisor first checks that the plugin's safety hooks are running. If it says "enforcement off", your organization's settings are blocking plugin hooks. See When things go wrong.

Amber = you type an approval phrase. Stages 9–12 repeat once per execution group in the plan. Most changes take 2–4 groups.

To start or resume: open Claude Code in the repo as the supervisor, claude --agent plan:supervisor (recommended, see Running with subagents), or in any session say be the supervisor. The supervisor reads plans/, tells you where every milestone stands and the one next step, and waits for you. You can close the session at any point. The next one picks up from the files.

Running with subagents

For clean context separation, run the supervisor as your main session and let it dispatch every role as a subagent. Each role then works in its own context and sees only the files the supervisor hands it.

cd your-repo
claude --agent plan:supervisor          # add --plugin-dir …/plugins/plan until 3.0 is published

To make this the default in a repository, add "agent": "plan:supervisor" to that repository's .claude/settings.json. (--agent supervisor works too.)

Why this layoutWhat it means for you
Approvals only count from youType every approval phrase in this main session. A phrase inside a prompt that an agent writes for a subagent records nothing; this was tested.
Each role has its own contextThe product owner, architect, engineers (up to 5 in parallel, one worktree each), auditor, and any checks you accept run as plan:<role> subagents.
Panels still fan outA validator or deliberator dispatched as a subagent starts its own skeptics or delegates; nested dispatch was tested.

Things to know

  • Agents, not role skills, when you want separation. A skill such as /plan:architect loads into your current context; an agent gets its own. The utility skills (/plan:swarm-init, /plan:swarm-metrics) are fine to run from the supervisor session.
  • The Grill Loop as a subagent. The product owner is written to return its open questions in its report, and the supervisor relays them to you. If you'd rather be questioned live, run that stage as claude --agent plan:product-owner.
  • Not every role can dispatch. The architect and product owner deliberately have no Agent tool; the supervisor, validators, and deliberators do.

Stages

1 · Raise an intent you product owner

Say what's wrong and what "done" looks like. Don't design the solution yet.

You do
  • Tell the supervisor what you want, in plain words. Or copy the template into plans/intents/ yourself.
  • Answer a few quick questions about the problem, who's affected, and constraints.
Swarm does
  • The product owner (intent mode) drafts the intent with you.
  • A deterministic script proposes a risk tier from the wording.
› Login gets brute-forced. Limit failed attempts per account and per IP.
supervisor ▸ Drafting an intent with the product owner…
           ▸ Wrote plans/intents/2026-09-24-login-rate-limit.md
           ▸ Proposed tier: routine (no keyword matched yet; re-checked once the plan names files)
Files you'll see
plans/intents/2026-09-24-login-rate-limit.md
  ## Problem · ## Outcome · ## Users & systems · ## Constraints · ## Open questions
Done when the intent file exists in the inbox. Nothing is committed yet.

2 · Accept the intent you approve

Decide whether this becomes work, and give it a milestone name.

You type
approve intent login-rate-limit as login-rate-limit

To reject it instead, tell the supervisor to close it. The file stays in history.

Swarm does
  • Creates the branch swarm/login-rate-limit (PR mode). Everything for this milestone, from here on, is committed there.
  • Moves the intent into plans/active_milestones/login-rate-limit/intent.md.
  • Adds a roadmap entry and commits both.
  • Logs your approval in approvals.md.
Done when the commit exists and the milestone folder appears.

Typing just "yes" or "ok" doesn't count. Approvals need the exact phrase, and the supervisor always shows it to you.

3 · Research automatic

Learn how the codebase handles this area today.

An explorer agent reads the relevant code and appends a Codebase context section to intent.md: affected modules, existing patterns, constraints. You don't need to do anything. Read the section if you want to check it found the right code.

Done when intent.md has a Codebase context section. It's committed with the spec later.

4 · Write the spec you answer + approve product owner

Turn the intent into testable requirements. What and why, never how.

You do
  • Answer the Grill Loop: at most 3 questions at a time, about edge cases, limits, errors, and UX.
  • Read spec.md, then approve it.
Swarm does
  • Writes spec.md with Given/When/Then acceptance criteria.
  • Loads your policy skills (for example security) and lists any Policy Concerns it can't resolve alone.
product-owner ▸ 1. After how many failed attempts should an account lock? For how long?
              ▸ 2. Should the lockout message reveal that the account exists?
              ▸ 3. Do trusted internal IPs bypass the per-IP limit?
› 5 in 15 min, lock 15 min. No, generic message. No bypass.
…
supervisor ▸ spec.md is ready. To accept it, type: approve spec login-rate-limit
approve spec login-rate-limit
Optional here

swap‑in Ask for the visual product owner to also get visual-spec.html: user‑story cards, flows, color‑coded criteria. Same spec.md underneath.

Done when spec.md (and intent.md's research) is committed and your approval is logged.

If you don't know an answer, say so. The product owner won't guess an edge case. It records the open question instead.

5 · Check the spec optional · offered

Find holes in the spec while they're cheapest to fix.

The supervisor offers two checks, with a one‑line reason, and recommends them for elevated and critical tiers. (Our example is still routine here. Its tier rises at planning.)

OptionWhat it doesAccept when
spec‑deliberator add‑onThree delegates, each holding different knowledge (product, engineering, ops/security), discuss and agree on one revised spec.The requirements depend on things different teams know: security policy, infra limits, product research.
spec‑validator offered gateThree independent skeptics attack the spec for ambiguity, gaps, and untestable criteria. Only issues found by 2 of 3 count.Auth, payments, personal data, public APIs, or any spec you'd hate to re‑plan.

If the validator finds issues, the product owner fixes the spec. Reviewers never edit what they review. Reports land in adversarial-reviews/ and deliberations/.

Done when you've accepted or declined each offer. Declines are logged with the tier, so skipped checks stay visible.

6 · Write the plan architect

Turn the spec into small, test‑first steps grounded in the real code.

The architect reads the code (it can't change it) and writes plan.md. Tasks are grouped into execution groups. Tasks inside a group touch different files, so they can be built in parallel. Every task starts with a test step. The plan also lists irreversible steps (migrations, deletions) and the proposed risk tier, re‑checked now that the affected files are known.

## Task Execution (Parallel Groups)
### Group 1  (parallel)
- [ ] Task 1.A: attempt counter store      → src/auth/attempts.ts
- [ ] Task 1.B: lockout response + message → src/auth/responses.ts
### Group 2  (after Group 1)
- [ ] Task 2.A: wire limiter into /login   → src/routes/login.ts
Optional here

swap‑in The visual architect also renders visual-plan.html: diagrams, a file map, annotated code. Same plan.md underneath.

Done when plan.md exists. You'll review it at stage 8.

7 · Check the plan optional · offered

Catch plan steps that can't work before any code is written.

OptionWhat it doesAccept when
plan‑deliberator add‑onDelegates each own a territory (the spec's intent, parts of the codebase, the delivery pipeline) and agree on one revised plan, deciding open trade‑offs.The plan spans several subsystems, or leaves a choice open (online vs offline migration, group boundaries).
plan‑validator offered gateThree skeptics open the files the plan relies on and look for the first domino: the earliest step whose failure breaks the rest.Irreversible steps, code the architect didn't open, or several subsystems.

Confirmed fixes go back to the architect, who updates the plan.

8 · Approve the plan you approve 🛑

The big go/no‑go. After this, code gets written.

You do
  • Read spec.md and plan.md (or the visual HTML), plus the one‑line verdict from every check that ran.
  • Confirm or change the risk tier.
Swarm does
  • Commits the plan and any check reports.
  • Logs the approval and the confirmed tier.
supervisor ▸ Spec and plan are ready. plan-validator: 0 confirmed · first_domino: none.
           ▸ Tier raised routine → critical at planning (path **/auth/** matched).
           ▸ To approve, type: approve plan login-rate-limit
           ▸ (to change the tier: approve plan login-rate-limit tier=elevated)
approve plan login-rate-limit
Done when the plan is committed on swarm/login-rate-limit. Engineers can't start before this. A hook blocks them.

Lowering a tier is allowed, but only by writing tier=… in this phrase, so the choice is on the record. The swarm can raise the tier later on its own, never lower it.

9 · Build engineer × up to 5

Implement one execution group, test‑first.

  • The supervisor starts one engineer per task in the current group, up to 5 at once. Each works in its own git worktree (a separate checkout), so builds and test runs never collide.
  • Engineers follow strict TDD: failing test → make it pass → tidy. They tick the task's boxes in plan.md.
  • Engineers may save work‑in‑progress commits on their own worktree branch (swarm-wip/login-rate-limit/1.A). These never get pushed.
  • When the group is done, the supervisor squashes all worktrees into the milestone branch without committing, so the audit sees one clean diff.
Optional here

add‑on simplifier: a clarity‑only tidy of the group's code (no behavior change) before the audit.

Done when every task in the group is ticked and the squash applied cleanly.

An engineer that hits a wrong plan step stops with blocked and a proposed fix. The supervisor shows it to you, and on your OK the architect updates the plan, which you re‑approve. A squash conflict means two tasks touched the same file. That's a plan problem, handled the same way.

10 · Audit auditor

Prove the group does what the plan says, with evidence.

  • Checks every step against the plan and cites file:line.
  • Runs your build and tests (from AGENTS.md or CLAUDE.md).
  • Hunts shortcuts: TODOs, placeholders, skipped or gutted tests, hard‑coded answers. Any new behavior without tests is an automatic FAIL.
  • Writes audit.md (tracked in git) with PASS or FAIL.
Done when the audit says PASS. On FAIL, the failing task goes back to an engineer automatically.

After 3 failed rounds on the same task, the swarm stops and asks you: re‑plan, drop the task, or take over.

11 · Check the code optional · offered

A skeptical second look at the diff before you commit it.

OptionWhat it doesAccept when
implementation‑validator offered gateThree skeptics try to break the diff. Its most useful output is corrected severity: it tells you which alarms are really critical and which only matter under rare conditions.Concurrency, shared state, changed error handling, security‑sensitive code.
visual recap add‑onRenders visual-recap.html: every changed file, annotated diffs, the audit verdict. On by default for elevated and critical tiers.You want to review the change at a glance rather than read a raw diff.

Confirmed defects go back to an engineer, highest severity first, and are re‑audited.

12 · Commit the group you approve 🛑

Turn the audited group into one commit.

supervisor ▸ Group 1 is verified (audit PASS).
 src/auth/attempts.ts      | 64 ++++++
 src/auth/responses.ts     | 22 ++
 test/auth/attempts.test.ts| 88 ++++++++
           ▸ Message: feat(auth): per-account and per-IP attempt counters with lockout
           ▸ To commit, type: approve commit login-rate-limit g1
approve commit login-rate-limit g1
auditor ▸ committed 4e1b0c2 on swarm/login-rate-limit

Only the auditor commits, and only with your fresh approval. The approval expires after 15 minutes and is tied to the current branch state. Then the swarm goes back to stage 9 for the next group.

Done when the group commit exists. After the last group, move on to the PR.

13 · Pull request you approve CI code owner merges

Put the change in front of your normal review process.

You type
approve pr login-rate-limit
Swarm and CI do
  • Record your PR approval in a small ledger‑only commit, then push swarm/login-rate-limit and open a PR. Its body links the intent and shows each group, every check's verdict, any skipped checks, the audit, the approvals, and the recap.
  • CI checks that every commit has an approval row, reviews the PR against REVIEW.md, and at elevated or critical tier runs the implementation validator on the PR.

A code owner merges on GitHub. The swarm never merges or pushes to your main branch. If review finds problems, the swarm runs a fix group (build → audit → approve commit) and updates the same PR. No new PR approval is needed.

Optional here

swap‑in Local mode (delivery.mode: local in swarm.md) skips the PR. Commits land on your current branch, and the approval log marks it.

Done when the PR is merged. The supervisor sees it next time and marks the milestone complete.

14 · Release you approve

Tag a version once every milestone in it is done.

supervisor ▸ All milestones for v1.4.0 are complete. To tag, type: approve release v1.4.0
approve release v1.4.0

Before asking, the supervisor switches to the default branch and updates it with git pull --ff-only (two separate commands). It then creates an annotated tag, asks before pushing it, and the product owner marks the release Shipped in the roadmap and activates the next one.

15 · Maintain future

Let production problems start the loop on their own. A human still decides.

A scheduled CI job watches the signals listed in bands.md. When one drifts far enough, a triage agent writes an evidence‑backed intent and the workflow opens it as a small PR. Merging that PR is accepting the intent, and it then enters stage 2 like any other. The triage agent can only write intents. It can't plan, code, or commit.

Approval phrases (cheat sheet)

Type exactlyStageWhat it unlocks
approve intent <slug> as <milestone>2Milestone and branch swarm/<milestone> created (PR mode), intent committed
approve spec <milestone>4Spec committed. Planning can start
approve plan <milestone> [tier=…]8Plan committed, tier confirmed, engineers allowed
approve commit <milestone> g<n>12One group commit
approve pr <milestone>13Record the approval, push, and open the PR
approve release <version>14Tag the release

The phrase must be the whole message. "Looks good, approve plan login-rate-limit" doesn't count, so a stray "yes" never approves anything. Each phrase works once and expires after 15 minutes.

Choosing the options

If your change…Say yes to
is small and easy to undoNothing extra. Decline the checks and keep moving.
touches auth, payments, personal data, or a public APIspec‑validator, plan‑validator, implementation‑validator (the supervisor will recommend them)
depends on rules owned by several teamsspec‑deliberator, then spec‑validator
spans several subsystems or has a migrationplan‑deliberator, then plan‑validator
adds concurrency or changes error handlingimplementation‑validator
needs stakeholders to review it visuallyvisual product owner / visual architect / visual recap
is a solo or offline spikelocal mode in swarm.md

Each check costs a small panel of agents, and usage.md shows the cost. Declining is fine, and it's recorded with the risk tier.

Risk tiers: what they mean for you

TierTypical trigger (from swarm.md)What changes
routineeverything elseChecks are offered, not pushed.
elevatedpublic API, cache, schema, large diffsThe supervisor recommends the validators. Recap on by default.
criticalauth, payments, migrations, PII, deletionsRecommends deliberator → validator and a stricter vote (any single skeptic can flag).

A script proposes the tier at stage 1, re‑checks it at stage 6 and before the PR, and can only raise it. You confirm it at stage 8. Tiers never force a check. You always choose.

When things go wrong

You seeWhyDo this
"enforcement off"Organization settings block plugin hooksAsk your platform team to add the swarm's gate as a managed hook (template provided). The supervisor won't run gated steps until then.
"no approval for commit/…/g2"Phrase missing, mistyped, expired, or already usedType the phrase the supervisor just showed, exactly.
"approval is stale: HEAD moved"Something was committed after you approvedThe supervisor re‑shows the diff. Approve again.
engineer reports blockedA plan step doesn't match the codeReview the proposed fix. The architect updates the plan, and you re‑approve it.
"escalating: 3 failed audit rounds"The task keeps failingChoose: re‑plan the task, drop it, or finish it yourself.
squash conflictTwo tasks in a group touched the same fileSame as blocked: the architect fixes the group boundaries.
tier raised before PRThe real diff touched riskier paths than plannedRe‑confirm with approve plan … tier=….
"swarm.md: no valid swarm-config block"The JSON block in plans/swarm.md is missing or brokenFix the block. Gated steps are refused until it parses.
"plans/swarm.md is missing in a plan-swarm repository"The settings file was deleted after setupRestore it from git. To stop using the swarm in this repo on purpose, delete .git/plan-swarm/active yourself.
"name the remote and the ref explicitly" · "run git commands directly"The gate only accepts forms it can checkThe supervisor pushes with git push origin swarm/<milestone> and never wraps git in other commands; if you see this, it tried a shortcut.
push refused: "has no matching approval in approvals.md"A commit on the branch was made without an approval (the pre‑push hook checked every commit)Find the commit in git log; redo it through the swarm, or remove it yourself.

What the swarm guarantees

  • No code before you approve the plan. Engineers can't be started until approve plan.
  • No commit, push, or tag without your phrase. Enforced by Claude Code hooks and three git hooks, not by agents promising to behave. These local checks stop agents from taking shortcuts; your host's branch protection and code‑owner review remain the final authority.
  • Reviewers never edit what they review. Validators and the auditor report. Engineers fix.
  • No untested code passes the audit.
  • Nothing lands on your main branch directly. Merges happen in your PR tool, by a code owner.
  • Everything is in git. Intent, spec, plan, audit, approvals, and cost are all committed.
  • You can always resume. The state is the files, not the chat.

Glossary

MilestoneOne change (feature, fix, refactor) with its own folder under plans/active_milestones/.
IntentA short statement of the problem and desired outcome. The start of every milestone.
Grill LoopThe product owner's short rounds of questions that turn vague requests into precise requirements.
Execution groupA set of plan tasks that touch different files and can be built in parallel. One commit per group.
WorktreeA separate checkout of the repo, one per engineer, so parallel work doesn't collide.
ValidatorA panel of 3 independent skeptics that attacks a spec, plan, or diff. An issue counts when 2 of the 3 find it.
DeliberatorA panel of delegates with different knowledge who agree on one improved spec or plan.
First dominoThe earliest plan step whose failure would break every step after it.
Severity calibrationThe implementation validator's corrected rating of how bad each confirmed defect really is.
Risk tierroutine · elevated · critical. Decides how strongly checks are recommended.
Approval phraseThe exact text you type to unlock a gated step. Single use, expires in 15 minutes.
Local modeA delivery setting that commits to your current branch without opening a PR.
