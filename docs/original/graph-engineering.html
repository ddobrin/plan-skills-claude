Graph Engineering and the Plan Swarm

What the term actually asserts, how much of it this plugin already satisfies, and the one thing it is structurally unable to see.

Update: the changes described here are implemented on branch plan-graph. For what shipped against each assertion, with the generated topology and the before/after diagrams, see Graph Conformance.

28 August 2026 ddobrin/plan-skills-claude companion to the suitability analysis implemented on branch plan-graph

The claim, reduced

Three assertions, and everything else is vocabulary

“Graph engineering” surfaced around July 2026 as the successor term to context, harness, and loop engineering. No Anthropic surface uses it. Stripped of the marketing, it asserts three things:

  • The topology should be an explicit artifact. Which nodes exist, who routes to whom, and under what condition — readable as one diagram, not inferred from prose.
  • Each node should get its own clean context. Different prompts, different tools, different evidence per node, so one agent's working memory does not pollute another's.
  • State should cross node boundaries only through declared edges. A schema, not a convention.

LangChain — who shipped the runtime the term describes — put the honest framing on it: “loops are simple graphs… a loop is just a directed, cyclic graph.” You do not graduate from loops to graphs. You compose loops into graphs when one loop stops being enough. That already happened here, long before the word existed.

So for this project the term is not prescriptive. It is a diagnostic checklist, and the swarm scores unevenly against it.

Two of the recommended changes — making the topology a generated artifact, and declaring a state.json per milestone — are pure graph engineering. They are the term paying rent.

The blind spot

A topology cannot show you whether its parallel branches are independent

The highest-value change identified in the analysis is not graph engineering, and graph engineering has no way to detect it.

The validator panels are drawn correctly as a graph: fan out to three, join on a quorum. The topology is right. The diagram is right. And the panel still behaves close to a single agent, because three identical prompts on one model produce correlated errors. You can satisfy every graph-engineering principle perfectly and still have a three-way fan-out carrying one vote.

The measurements behind this sit outside the graph literature entirely. Correlated judge panels run 8–22 points below the independent-voting ideal, and no aggregation algorithm recovers more than 11% of that gap. Only about 10% of size-3 ensembles beat their own strongest member. None of that is expressible as topology; all of it decides whether the gate works.

The takeaway from the original question

Graph engineering gave a good checklist for the shape of this system and was silent on the thing that mattered most. That is worth knowing before adopting any successor term: these frameworks describe how work is routed, not whether the work being routed is any good.

The deliberators are the interesting case

Graph engineering has no name for them, and the omission is structural rather than accidental. A graph models routing: node A finishes, an edge carries its output to node B. Delegates holding disjoint territories, taking sequential turns relayed verbatim, continued across rounds until they converge on one revised artifact, is not an edge — it is a conversation. There is no arrow that means “argued until they agreed, and each acceptance had to state its basis.”

So the deliberators are simultaneously the part of this system the graph vocabulary describes worst, and — by the correlation evidence — the part that gets independence most right. Their Core Principle 1 is a precise statement of decorrelation, complete with a falsifiable pre-flight check:

asymmetry is created by assigned investigation: each delegate deep-reads only its territory and becomes the panel's sole authority on it. Apply the asymmetry test: for each delegate, name one question about this plan that only its territory can answer. If you cannot, merge the territories and revise centrally instead.

The validators — which run far more often and hold the actual gates — do not apply this at all. The direction of borrowing should run from the deliberators to the validators, not the other way around.

The shape of that table is the answer to the original question. Chasing the term was worth it — it produced a real defect (assertion 1) and a real structural improvement (assertion 3). It did not produce the change that matters most, and it could not have.

Bottom line

How to describe this project

Not as graph engineering. No Anthropic surface uses the term, it will likely be superseded before it stabilizes, and adopting it would claim credit for the weakest part of the design while obscuring the strongest.

The defensible claim is stronger and more durable: a spec-driven swarm whose nodes have genuine context isolation and capability bounds, whose phase boundaries are guarded by adversarial panels, and whose irreversible steps are gated on a human. When precision is needed, use the vocabulary that will still parse in a year — orchestrator-workers, parallelization by voting, evaluator-optimizer, prompt chaining — all of which predate the buzzword and all of which this system implements.

The work stated without any framework at all was: make the topology a single artifact instead of three, declare the state instead of inferring it, and make the votes actually independent. All three are now implemented on plan-graph — two of them the graph literature helped with, and the third, where the points are, it could not see. What remains is measurement: re-run a shipped milestone with partitioned lenses and with identical ones, and diff the confirmed sets.
